# Отчёт

Клиент-серверное приложение NexaDesk: платформа совместной работы над задачами. Фронтенд и бэкенд разделены, общаются по HTTP/REST, данные хранятся в СУБД PostgreSQL, реализованы CRUD операции над сущностями доменной области. Ниже описана доменная область, стек, основные сущности и аргументация соответствия методологии 12 факторов.

## Доменная область

NexaDesk это инструмент для командной работы в стиле трекера задач. Работа организуется в проекты, проект разбивается на задачи, задачи двигаются по канбан-доске. Участники проекта имеют роли, назначают задачи друг другу, обсуждают их в комментариях с упоминаниями, группируют метками и следят за изменениями через уведомления и историю активности. Каждое изменение транслируется остальным участникам в реальном времени.

Основные сценарии:

* регистрация и вход, профиль пользователя
* создание проекта, приглашение участников, назначение ролей, передача владения
* канбан-доска с перетаскиванием карточек и порядком внутри колонок
* задачи: создание, редактирование с защитой от параллельных правок, назначение исполнителя, дедлайн, оценка в часах, подзадачи
* комментарии с упоминаниями пользователей
* метки, подписки на задачи, фильтры
* уведомления о назначениях, упоминаниях и изменениях в отслеживаемых задачах
* лента активности проекта и задачи, live-обновления по SSE

## Стек реализации

Бэкенд: Python 3.12, FastAPI, SQLAlchemy 2 (асинхронный), Alembic, Pydantic, PyJWT, Passlib (argon2), SlowAPI, sse-starlette.
Данные: PostgreSQL 16 (основное хранилище), Redis 7 (шина событий Pub/Sub, отзыв refresh-токенов, буфер повтора событий).
Фронтенд: React 19, TypeScript, Vite, React Router, TanStack Query, Zustand, dnd-kit, CSS Modules.
Инфраструктура: Docker, Docker Compose, nginx (раздача статики SPA и прокси /api, /health), GitHub Actions (CI).
Взаимодействие: HTTP/1.1 REST с JSON, авторизация по Bearer-токену и refresh-cookie, realtime по SSE поверх HTTP.

## Основные сущности доменной области

* User: учетная запись, username, email, хеш пароля (argon2), глобальная роль (user, admin), признак активности
* Project: проект с уникальным ключом, названием, описанием, владельцем и признаком архивности, хранит счетчик задач для проектной нумерации
* ProjectMember: участие пользователя в проекте с ролью (owner, admin, member, viewer), инвариант: ровно один владелец проекта
* TaskStatus: колонка доски проекта (название, ключ, цвет, позиция), при создании проекта добавляются колонки по умолчанию
* Task: задача с проектным номером вида DEMO-1, заголовком, описанием, статусом, приоритетом, автором, исполнителем, родительской задачей, дедлайном, оценкой в часах, порядком на доске, версией для оптимистической блокировки (If-Match) и мягким удалением
* Comment: комментарий к задаче с автором и текстом, при сохранении разбираются упоминания, удаление мягкое
* Label: метка проекта (название, цвет), название уникально в рамках проекта
* TaskLabel: связь задачи и метки
* TaskWatcher: подписка пользователя на задачу, включение и выключение идемпотентны
* ActivityEvent: событие истории (тип, проект, задача, автор, данные), хранится как append-only журнал, питает ленту активности и повтор событий для SSE
* Notification: уведомление пользователя (тип, снимок данных задачи, автор изменения, признак прочтения)

CRUD реализован над всеми сущностями через REST API, контракт описан в docs/api-endpoints.md. Удаление задач и комментариев мягкое, остальные операции физические.

## Соответствие методологии 12 факторов

## I. Codebase

Одна кодовая база в git, множество деплоев. Monorepo содержит backend, frontend и документацию; из него собирается и локальная разработка, и деплой на сервер. Каждый деплой привязан к конкретному коммиту через сборку образов из этого репозитория. Продукт состоит из двух приложений (API и веб-клиент) в одной кодовой базе, они версионируются и тестируются вместе.

## II. Dependencies

Зависимости объявлены и изолированы. Бэкенд: pyproject.toml и poetry.lock, при сборке образа зависимости экспортируются из lock-файла и ставятся в изолированный слой. Фронтенд: package-lock.json и npm ci. Системные пакеты ставятся только в стадию builder, рантайм-образ их не содержит. Установки пакетов вручную на окружении не требуется.

## III. Config

Конфигурация хранится в переменных окружения и строго отделена от кода. pydantic-settings читает окружение: DATABASE_URL, REDIS_URL, секреты JWT, CORS, настройки cookie, лимиты и параметры SSE. Значения для разработки и эксплуатации отличаются только содержимым окружения, не кодом. Файл .env не попадает в репозиторий, его структура описана в .env.template. Приложение валидирует конфигурацию при старте и отказывается работать с дефолтными секретами. Значение VITE_API_URL фронтенда зашивается при сборке, но в данном деплое оно пустое: клиент ходит относительными путями через nginx, поэтому образ веб-клиента один для всех окружений.

## IV. Backing services

База данных и кэш это присоединяемые ресурсы. Приложение обращается к PostgreSQL и Redis только по URL из конфигурации; другой экземпляр или другой сервис подключается заменой URL без правок кода. Долговременные данные лежат в PostgreSQL, Redis служит шиной событий и хранилищем отзывных токенов, то есть не является источником истины. Потеря Redis деградирует в повтор событий из истории и повторную авторизацию, но не теряет данные.

## V. Build, release, run

Стадии строго разделены. Build: Dockerfile разделяет сборку зависимостей и рантайм, результат это неизменяемый образ. Release: образ комплектуется конфигурацией окружения, схема базы обновляется отдельным релизным шагом (одноразовый сервис migrate). Run: запуск контейнеров из готовых образов, код при запуске не меняется. CI собирает и проверяет оба компонента на каждый pull request.

## VI. Processes

Приложение выполняется как stateless-процессы. Долговременное состояние только в PostgreSQL, refresh-токены и их отзыв в Redis, access-токены стейтлесс (JWT), сессий в памяти процесса нет, файловая система контейнера для состояния не используется. Реестр открытых SSE-соединений живет в памяти процесса, но это эфемерное состояние: клиент переподключается и добирает события по Last-Event-ID из истории активности, а сами события распространяются через Redis Pub/Sub. Поэтому несколько экземпляров процесса API работают корректно, ничего не теряется при их перезапуске.

## VII. Port and binding

Сервис экспортирует HTTP-интерфейс через привязку к порту. uvicorn слушает 0.0.0.0:8000, nginx слушает порт 80 контейнера и публикуется на хосте. Приложение самодостаточно: оно не встраивается в веб-сервер как модуль, а nginx перед ним это самостоятельный ресурс, который раздает статику и проксирует API и поток событий.

## VIII. Concurrency

Масштабирование выполняется процессной моделью. Процессы stateless, состояние вынесено во внешние сервисы, значит число процессов можно увеличивать вертикально и горизонтально. Типы процессов: api (uvicorn), web (nginx) и разовый migrate. Отдельного типа фоновых воркеров нет и не требуется: асинхронный стек обрабатывает фоновые операции в рамках запроса и событий. Оговорка: в поставляемом compose поднимается по одному экземпляру каждого процесса. Для нескольких реплик API нужен балансировщик: в текущем конфиге nginx имя сервиса резолвится один раз при старте. Это ограничение примера развертывания, а не архитектуры приложения, приложение к масштабированию готово.

## IX. Disposability

Быстрый старт и корректная остановка. Процесс запускается за секунды, пулы соединений к PostgreSQL и Redis создаются на старте и корректно закрываются при остановке. Пробы /health/live (живость процесса) и /health/ready (готовность зависимостей) вместе с контейнерными healthcheck и условиями depends_on healthy дают правильный порядок запуска и остановки. SIGTERM обрабатывается uvicorn, запросы успевают завершиться, а прерванные SSE-потоки клиенты восстанавливают переподключением с повтором событий.

## X. Dev/prod parity

Разработка и эксплуатация максимально похожи. Один и тот же путь запуска (docker compose up --build), те же образы, те же миграции Alembic, одна форма описания конфигурации (.env.template). Различия сведены к явным и локальным: режим hot-reload в dev-композе бэкенда и dev-сервер Vite вместо nginx при фронтенд-разработке. CI на каждый pull request запускает линтинг, проверку типов, тесты и сборку обоих компонентов, что удерживает код в рабочем состоянии. Оговорка: автоматического деплоя нет, релиз выполняется вручную сборкой и запуском compose на сервере, поэтому постоянной доставки в этом пункте нет.

## XI. Logs

Логи обрабатываются как поток событий. Приложение пишет логи в stdout через logging.StreamHandler, access log uvicorn также идет в stdout. nginx пишет access и error логи в stdout и stderr. Файлы логов внутри контейнеров не используются, сбор и просмотр через драйвер логов Docker (docker compose logs), при необходимости поток направляется во внешнюю систему сбора логов без изменения приложения.

## XII. Admin processes

Административные и разовые задачи выполняются одноразовыми процессами в том же окружении, что и приложение. Миграции схемы базы: одноразовый сервис migrate из того же образа с той же конфигурацией (alembic upgrade head), команда make migrate для ручного запуска и make makemigrations для создания новой миграции. Управление выполняется теми же инструментами и теми же переменными окружения, что и в рантайме.

## Запуск приложения

```
cp .env.template .env
# заполнить секреты, каждый генерируется командой openssl rand -hex 32
docker compose up --build
```

Миграции применяются автоматически. Веб-интерфейс: http://localhost:8080, Swagger: http://localhost:8000/docs.

Проверка качества: в backend выполняются black, ruff, mypy и pytest, в frontend lint, typecheck и сборка, те же команды запускает CI.
