# Отчёт

Мониторинг приложения NexaDesk в minikube: экспорт метрик приложения и PostgreSQL в TSDB Victoria Metrics по модели Pull с автоматическим обнаружением таргетов.

## Стек мониторинга

* Victoria Metrics single-node (TSDB), helm-чарт vm/victoria-metrics-single 0.13.10, релиз vmsingle в namespace observability, установка через helmfile (k8s/observability/helmfile.yaml)
* Сбор метрик выполняет скрейпер, встроенный в vmsingle (флаг -promscrape.config), конфигурация скрейпа лежит в ConfigMap и монтируется в под; отдельный vmagent не разворачивается, его роль выполняет встроенный скрейпер
* Обнаружение таргетов через kubernetes_sd_configs, интервал скрейпа 15 секунд
* Помимо приложения скрейпятся сама Victoria Metrics, API-сервер Kubernetes, ноды и cadvisor
* Доступ к Victoria Metrics: HTTP API на порту 8428, для проверки используется kubectl port-forward

## Экспортер метрик рантайма

Экспорт реализован библиотекой prometheus_client, встроенной в приложение (Python, FastAPI).

* Метрики отдаются на выделенном порту 9100 по пути /metrics без авторизации; порт опубликован отдельным Service, не заведён в Gateway, а NetworkPolicy разрешает доступ к нему только из namespace observability
* Формат выдачи OpenMetrics 1.0.0; заголовок Accept может согласовать классический текстовый формат Prometheus
* Метрики рантайма: python_gc_collections_total, python_info, process_cpu_seconds_total, process_resident_memory_bytes, process_open_fds, process_num_threads и другие коллекторы библиотеки
* RED-метрики HTTP собственного middleware: http_requests_total (метод, шаблон маршрута, код ответа), http_request_duration_seconds (гистограмма по методу и маршруту), http_requests_in_progress (число запросов в обработке), app_info (сервис и версия сборки)
* Скрейпы /metrics и пробы /health не попадают в HTTP-метрики, чтобы не искажать данные; незнакомые пути сводятся к одному значению лейбла route, чтобы произвольные запросы не раздували кардинальность

## Экспортер метрик PostgreSQL

Использован готовый экспортер postgres-exporter (образ bitnami/postgres-exporter), добавленный контейнером в под PostgreSQL: контейнеры пода имеют общее пространство портов, экспортер слушает 9187.

* Экспортер включён в values чарта bitnami/postgresql (metrics.enabled), там же задана NetworkPolicy, разрешающая скрейп из namespace observability
* Экспортируемые метрики: pg_up, pg_stat_database_* (транзакции, блоки, дедлоки, temp-файлы), pg_stat_activity_count, pg_database_size_bytes, pg_locks_count, pg_replication_lag_seconds, pg_wal_size_bytes, pg_settings_*, pg_exporter_*
* Аннотации prometheus.io/* на поде PostgreSQL передают порт 9187 и путь /metrics, таргет обнаруживается автоматически

## Бизнес-метрики приложения

Реализовано семь бизнес-метрик доменной области (задачи, комментарии, уведомления, авторизация, realtime):

* nexadesk_tasks_created_total, Counter, лейбл priority - созданные задачи по приоритету
* nexadesk_tasks_transitions_total, Counter, лейблы direction и result - попытки смены статуса задачи: направление по доске (forward, backward, same) и исход (success, conflict, error)
* nexadesk_comments_created_total, Counter, лейбл has_mentions - комментарии к задачам по наличию разобранных упоминаний пользователей
* nexadesk_notifications_created_total, Counter, лейбл type - созданные уведомления по типу
* nexadesk_auth_attempts_total, Counter, лейбл result - попытки авторизации по исходу: success, invalid_credentials, invalid_token, rate_limited, error
* nexadesk_sse_streams_active, Gauge - число открытых потоков SSE
* nexadesk_tasks_overdue, Gauge - просроченные задачи, значение обновляется фоновым снимком из базы

Метрики инкрементируются в сервисном слое приложения при создании задач, комментариев и уведомлений, при смене статуса и авторизации, число потоков публикуется при открытии и закрытии SSE-соединений. Серии событийных счётчиков появляются после первого соответствующего события, поэтому для демонстрации нужна активность в приложении.

## Service discovery

Таргеты описаны не статически, а обнаруживаются по аннотациям подов:

* prometheus.io/scrape: "true", prometheus.io/port, prometheus.io/path заданы на шаблоне пода деплоймента backend и на поде PostgreSQL (k8s/environments/dev/app-values.yaml, k8s/environments/dev/postgres-values.yaml)
* Job nexadesk-pods в scrape-конфиге Victoria Metrics: kubernetes_sd_configs с role pod, отбор подов по аннотации prometheus.io/scrape, порт из аннотации сопоставляется с портом контейнера (keep_if_equal), путь из аннотации подставляется в __metrics_path__
* Новые поды приложения и базы подхватываются мониторингом автоматически, без правки конфигурации

## Развёртывание и проверка

Развёртывание: helmfile sync из каталога k8s ставит приложение, PostgreSQL и Redis, каталог k8s/observability применяется командой kubectl apply -f observability/ -R.

Проверка подов и сервисов:

```bash
kubectl get pods -n observability
kubectl get svc -n observability
```

Проброс портов и проверка сбора метрик:

```bash
kubectl port-forward svc/vmsingle-victoria-metrics-single-server -n observability 8428:8428
curl "http://localhost:8428/api/v1/label/__name__/values"
curl "http://localhost:8428/api/v1/query?query=up"
curl "http://localhost:8428/api/v1/query?query=nexadesk_auth_attempts_total"
curl "http://localhost:8428/api/v1/query?query=pg_up"
```
