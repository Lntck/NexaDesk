# Отчёт по развёртыванию NexaDesk в Kubernetes

Каталог k8s содержит декларативные манифесты для запуска приложения в кластере Kubernetes. Ниже описаны использованные абстракции Kubernetes и схема взаимодействия сервисов приложения.

## Абстракции Kubernetes

Namespace

* Namespace nexadesk изолирует все объекты развёртывания от остального кластера.

Конфигурация и секреты

* ConfigMap app-config: некритичные настройки (имя базы, URL Redis, сроки жизни токенов, CORS, параметры SSE). Монтируется в поды как переменные окружения через envFrom.
* Secret app-secrets: пароль PostgreSQL, строка подключения DATABASE_URL, секреты JWT. Тоже передаётся через envFrom. Отделение конфигурации от кода соответствует III фактору методологии.

Вычислительные ресурсы

* Deployment backend: API на FastAPI (uvicorn, порт 8000). Безсостоятельный процесс, поэтому используется Deployment: можно свободно менять число реплик и выполнять плавные обновления. Заявлены ресурсы (requests и limits), readiness-проба по /health. Init-контейнер wait-for-migrations держит старт приложения до применения миграций (проверяет alembic current на наличие head).
* Deployment frontend: nginx с собранной SPA React (порт 80). Имеет readiness и liveness пробы по корню, небольшие ресурсы. Переменная API_UPSTREAM передаёт адрес бэкенда в шаблон nginx.
* StatefulSet db: PostgreSQL 16. StatefulSet выбран потому, что базе нужно постоянное хранилище: через volumeClaimTemplates создаётся PersistentVolumeClaim data (1Gi, ReadWriteOnce) и закрепляется за экземпляром. Readiness-проба по pg_isready.
* StatefulSet redis: Redis 7 с AOF (appendonly yes), аналогично с PersistentVolumeClaim на 1Gi и пробой redis-cli ping. Хранит шину событий Pub/Sub и отзыв refresh-токенов.
* Job migrate: одноразовая задача alembic upgrade head из того же образа, что и бэкенд. Init-контейнер wait-for-db ждёт готовности PostgreSQL утилитой pg_isready. Ограничены число повторов (backoffLimit 3) и время жизни завершённой задачи (ttlSecondsAfterFinished 300). Миграции вынесены в отдельный релизный шаг (V фактор), а не в старт приложения.

Сетевые абстракции

* Service backend: ClusterIP, порт 8000, селектор по меткам компонента.
* Service frontend: ClusterIP, порт 8080 наружу, пробрасывается на порт 80 контейнера.
* Service db: headless (clusterIP None), нужен для стабильной сети StatefulSet и обращения по имени db:5432.
* Service redis: ClusterIP, порт 6379.
* Gateway API (gateway.networking.k8s.io/v1): GatewayClass envoy-gateway описывает контроллер Envoy Gateway, Gateway nexadesk поднимает HTTP-листенер на порту 80 и разрешает маршруты только из своего пространства имён. HTTPRoute api направляет префиксы /api и /health на backend:8000, HTTPRoute web направляет всё остальное на frontend:8080. Таймауты запросов в api-маршруте отключены (0s), чтобы не обрывались долгоживущие SSE-потоки.

Соглашения

* Единые метки app.kubernetes.io/name и app.kubernetes.io/component связывают селекторы, сервисы и поды между собой.
* Порядок применения задан именами файлов: 00-namespace, 01-configmap, 02-secret, затем компоненты.

## Взаимодействие сервисов

Схема трафика:

```
браузер
   |
   | HTTP :80
   v
Gateway (Envoy, Gateway API)
   |-- /api, /health --> Service backend:8000 --> Pod backend (FastAPI)
   |                                              |-- PostgreSQL: Service db:5432
   |                                              +-- Redis: Service redis:6379
   +-- /* ------------> Service frontend:8080 --> Pod frontend (nginx)
                                                  +-- proxy /api, /health --> Service backend:8000
```

Потоки запросов

* Внешний клиент обращается к единой точке входа: Gateway слушает порт 80. Путь /api и /health идёт напрямую в API, всё остальное в веб-клиент. Маршрутизация выполняется по префиксу пути средствами HTTPRoute, балансировка между репликами выполняется Service.
* Браузер ходит к API относительными путями, поэтому запросы могут идти как через Gateway напрямую в backend, так и через nginx фронтенда: location /api и /health в nginx.conf проксируются на API_UPSTREAM (backend:8000). Так сохраняется same-origin для refresh-cookie. Внутренний прокси выключает буферизацию (proxy_buffering off) и ставит длинный read-таймаут, чтобы SSE-потоки не обрывались.
* API и веб-клиент не связаны жёстко: фронтенд узнаёт адрес бэкенда только из переменной окружения API_UPSTREAM, то есть замена адреса не требует пересборки образа.

Потоки данных

* backend обращается к PostgreSQL по DATABASE_URL из Secret (хост db, порт 5432). Headless Service даёт стабильное имя экземпляра StatefulSet.
* backend обращается к Redis по REDIS_URL из ConfigMap (redis://redis:6379/0): публикация событий realtime и хранение отзыва refresh-токенов.
* Значения попадают в контейнеры через envFrom из ConfigMap и Secret, поэтому состав сервисов задаётся конфигурацией, а не кодом.

Порядок запуска и согласованность

* Job migrate выполняется после готовности PostgreSQL (init-контейнер wait-for-db) и применяет схему.
* Поды backend стартуют только после того, как миграции дошли до head (init-контейнер wait-for-migrations): исключается работа приложения с неактуальной схемой.
* Readiness-пробы убирают неготовые поды из балансировки: backend через /health, frontend через корень, db и redis через клиентские утилиты.

## Итог

Развёртывание описано декларативно и разделено на слои: изоляция (Namespace), конфигурация (ConfigMap, Secret), вычислительные ресурсы (Deployment для stateless-частей, StatefulSet с PersistentVolumeClaim для хранилищ, Job для миграций), сеть (Service, headless Service) и внешний трафик (Gateway API: GatewayClass, Gateway, HTTPRoute). Сервисы связаны через Service-имена и переменные окружения: клиент к Gateway, Gateway к frontend и backend, nginx фронтенда к backend, backend к PostgreSQL и Redis. Такой порядок и форма связей позволяют менять число реплик и адреса сервисов без правок кода приложения.
