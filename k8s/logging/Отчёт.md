## Victoria Logs в minikube: отчёт по домашнему заданию

Развёрнута Victoria Logs (single-node) в том же minikube-кластере, где работает приложение из ДЗ №1. Приложение логирует JSON в stdout контейнера, логи всех подов доставляются в Victoria Logs, четыре LogsQL-запроса выполнены во встроенном vmui и задокументированы ниже со скриншотами. Бонусная часть (официальный Grafana-плагин Victoria Logs и алерт vmalert) выполнена, её отчёт лежит отдельно: k8s/monitoring/Отчёт.md.

## Состав стенда и манифесты

* k8s/logging/namespace.yaml - namespace logging для всей логовой инфраструктуры.
* k8s/logging/statefulset.yaml - Victoria Logs single-node: victoriametrics/victoria-logs:v1.53.0, данные на PVC 10Gi, retention 30 дней, порт 9428, пробы /health.
* k8s/logging/service.yaml - headless Service victorialogs.logging.svc:9428 (доступна из кластера и через kubectl port-forward снаружи).
* k8s/logging/vlagent-daemonset.yaml - шиппер логов (DaemonSet на каждый узел).
* k8s/logging/vlagent-rbac.yaml - ServiceAccount и права на чтение pods/namespaces/nodes (нужны шипперу для обогащения записей метаданными кубера).
* JSON-логирование приложения: backend/app/core/logger.py и backend/app/core/middleware.py (structlog), frontend/nginx.conf (log_format json с escape=json).


Почему Victoria Logs развёрнута так:

* StatefulSet, а не Deployment: стабильное имя пода и volumeClaimTemplates - данные переживают пересоздание пода, для хранилища логов это принципиально.
* Headless Service (clusterIP: None): однонодовая инстанция не нуждается в балансировке, DNS-имя victorialogs.logging.svc:9428 едино для всех шипперов и для port-forward.
* Single-node без кластеризации: по условию задания и для minikube это избыточная сложность; путь миграции на кластерную схему (vlcluster) от такой топологии не закрыт.
* Retention 30 дней и PVC 10Gi: ограниченный бюджет хранения под нагрузку учебного стенда, при этом запаса хватает на недели работы.
* Плейн-манифесты вместо Helm: весь стенд (приложение, БД, логи) собран в одном стиле - явно, читаемо, легко проверить при ревью; переход на Helm-chart victoria-logs-single потом сводится к переносу тех же значений в values.

## JSON в stdout: схема полей

Бэкенд (FastAPI, structlog) и фронтенд (nginx) пишут в stdout единообразные JSON-строки, одна строка - одна запись. Поля по чек-листу семинара и осмысленные дополнения:

* timestamp - ISO 8601, UTC, с миллисекундами (у nginx - время запроса).
* level - INFO / WARNING / ERROR (у nginx выводится из status_code через map: 5xx - ERROR, 4xx - WARNING, остальное - INFO).
* severity_number - числовой уровень в терминах OpenTelemetry, чтобы не писать маппинг в каждом инструменте.
* message - текст записи ("http request completed", "GET /api/v1/projects/2/tasks" и т.п.).
* service.name - nexadesk-backend / nexadesk-frontend; плюс service.version и deployment.environment.name - стандартные атрибуты OTel.
* k8s.pod.name, host.name - из какого пода запись (плюс kubernetes.* от шиппера: pod_namespace, container_name, pod_node_name).
* HTTP-контекст: method, path, status_code, duration_ms (у nginx duration_s и upstream_duration_s), user_id, bytes_sent, remote_addr, user_agent.
* request_id и trace_id - сквозная корреляция: nginx генерирует X-Request-Id и отдаёт его клиенту, бэкенд логирует то же значение, запрос можно найти на всех слоях по одному идентификатору.

Почему именно так:

* JSON разбирается Victoria Logs без grok-подобных правил: каждое поле сразу становится фильтром и ключом группировки (см. запросы ниже).
* Одинаковая схема у бэкенда и nginx позволяет искать по level и service.name единообразно, а не учить два формата.
* Query string намеренно не логируется (в ней бывают токены и секреты), секреты и пароли скраббятся до рендера записи.

## Доставка логов: почему выбран vlagent (DaemonSet)

Устройство: vlagent на каждом узле тейлит файлы подов (kubernetes collector читает /var/log и симлинки /var/log/containers), парсит JSON, обогащает записи метаданными кубера (pod_name, pod_namespace, container_name) и пишет в Victoria Logs нативным протоколом: -remoteWrite.url=.../insert/native.

Почему такой способ доставки:

* Шиппер от того же вендора, что и хранилище: нативный протокол вставки вместо совместимости с чужими API (ES-bulk, Loki), меньше трансформаций и точек отказа.
* Один DaemonSet на кластер вместо сайдкара в каждом поде: не нужно менять спеки приложения, автоматически покрываются и системные компоненты (postgres, сам vlagent), один конфиг на всё.
* Работает с Docker runtime minikube: симлинки /var/log/containers/*.log ведут в /var/lib/docker/containers/*/*-json.log, поэтому каталог примонтирован отдельно и read-only - узко, без чтения всего диска.
* Надёжность: чекпоинты позиций чтения в /var/lib/vlagent переживают рестарт пода (дублей и провалов нет), буфер на диск до 2 ГиБ (-remoteWrite.maxDiskUsagePerURL) - логи не теряются, если Victoria Logs временно недоступна.
* Безопасность: файлы ноды примонтированы read-only, readOnlyRootFilesystem, capabilities drop ALL плюс DAC_READ_SEARCH (чтение чужих файлов логов), seccomp RuntimeDefault.

Альтернативы и почему не они: Vector / Fluent Bit - универсальны, но это лишняя конфигурация и ещё один формат правил при том, что хранилище - Victoria Logs; OpenTelemetry Collector - оправдан, если в стеке уже есть OTel-пайплайн; прямой push из приложения - связывает приложение с конкретным хранилищем и теряет логи при его недоступности (у шиппера есть буфер).

## Четыре LogsQL-запроса в vmui

Запросы выполнялись во встроенном vmui (порт-форвард выше). Везде через Stream filters выбраны контейнеры backend и frontend, чтобы отсеять системные логи minikube (kube-apiserver, storage-provisioner и т.п.). Окно выбирается самим запросом (_time:15m), а не ползунком UI - так запрос остаётся воспроизводимым в любом инструменте.

(а) Сырые записи за последние 15 минут

```
_time:15m
```

![q1](../../img/q1.png)

Что показывает: 50 последних записей приложения в исходном виде - access-события nginx ("GET /api/v1/projects/2/board", "POST /api/v1/tasks/3/reorder") и события бэкенда ("http request completed"), уровни и полное содержимое полей записи. Всего 572 записи за окно, гистограмма сверху показывает распределение во времени.

Почему такой запрос: это базовый "живой поток" для разбора инцидента - сначала смотрят, что вообще происходило, потом уточняют фильтрами. Лимит 50 в UI задан, чтобы ответ оставался читаемым.

(б) Фильтр по конкретному полю: уровень ошибки

```
level:error _time:15m
```

![q2](../../img/q2.png)

Что показывает: за последние 15 минут записей уровня error нет (Total: 0) - нормальное состояние стенда. Работоспособность фильтра проверялась ранее на синтетических ERROR-записях, которые использовались для проверки алерта (см. бонус): тот же запрос их находил.

Почему такой запрос: level - главное поле нашей схемы; именно на нём построен алерт из бонусной части, то есть запрос из отчёта и правило алерта - одна и та же логика. Запись уровня error в vmui видна мгновенно после доставки (задержка шиппера - секунды).

(в) stats-запрос с группировкой: количество записей по уровням

```
_time:15m | stats by (level) count() as log_count
```

![q3](../../img/q3.png)

Что показывает: распределение записей за 15 минут по уровню: INFO 527, OTHER 44, WARNING 3. OTHER - записи без поля level: "сырые" строки postgres и стартовые сообщения процессов, у которых нет нашей JSON-схемы. Это нормально: шиппер не выбрасывает не-JSON строки, они доступны для поиска как есть.

Почему такой запрос: группировка count по level - самый быстрый способ оценить "здоровье" окна: сколько ошибок и предупреждений на фоне обычного трафика. По такому же принципу (stats by (...) count()) построены правила vmalert.

(г) Агрегирующий запрос: уникальные пользователи

```
_time:15m | stats count_uniq(user_id) as unique_users
```

![q4](../../img/q4.png)

Что показывает: 1 уникальный пользователь за последние 15 минут (считаются уникальные значения поля user_id из access-событий бэкенда).

Почему такой запрос: count_uniq - агрегат из рекомендованных (наряду с top и quantile), и он сразу применим к нашей схеме, потому что user_id логируется в каждом HTTP-событии. Альтернативы на тех же данных: top 5 (kubernetes.pod_name) по количеству записей - самые активные поды; quantile(0.99, duration_ms) - медианная и хвостовая задержка запросов. Выбран count_uniq, потому что он отвечает на продуктовый вопрос (сколько людей работает в системе), а не только на технический.
